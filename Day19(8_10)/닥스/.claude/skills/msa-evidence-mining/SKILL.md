# 근거 수집

## 왜 따로 떼어 놓는가

보고서에 들어가는 숫자(포트, 임계값, 데이터 행 수, 측정치)와 이름(클래스, 파일 경로,
Kafka 토픽)은 전부 검증 가능한 사실이다. 글을 쓰면서 기억에 의존해 채우면 거의 반드시
한두 개가 틀리고, 그 하나가 문서 전체의 신뢰를 깎는다.

그래서 **수집과 집필을 분리한다.** 이 스킬은 사실만 모으고 해석하지 않는다.

## 수집 순서

### 1. 교수님 코멘트부터 읽는다
무엇을 얼마나 깊이 쓸지가 여기서 정해진다. 이걸 마지막에 읽으면 이미 쓴 원고가
과제 범위를 벗어나 있다.

### 2. 팀 저장소의 readme와 `_workspace/`를 읽는다
잘 쓰인 저장소라면 readme가 이미 근거의 절반이다. 포트표, 도메인 매핑표, 알려진 한계,
측정 결과가 정리돼 있다. 여기 있는 것을 코드에서 다시 확인하려 들지 마라 — 시간 낭비다.

### 3. 흐름의 이음매만 코드로 확인한다
서비스 내부 구현이 아니라 **서비스와 서비스가 만나는 곳**을 본다. 그게 MSA 보고서의
소재이고, 실습 가이드가 "알아야 할 것"으로 지정한 범위와도 정확히 겹친다.

확인할 이음매 6곳:
- `docker-compose.yml`의 `depends_on` — 기동 순서가 왜 강제되는가
- `EUREKA_CLIENT_SERVICEURL_DEFAULTZONE` — 어느 서비스가 Eureka에 등록되는가
- Kafka Producer/Consumer 짝 — 토픽 이름, 이벤트 payload 필드
- Gateway 라우팅 규칙 — URL prefix 방식
- 서비스 간 동기 호출(WebClient/RestTemplate) 지점
- 프론트가 실제로 부르는 엔드포인트 목록

### 4. 팀이 바꾼 것을 원본과 대조한다
`msa-lecture/`(원본)와 팀 저장소를 같은 경로끼리 비교하면 "무엇을 커스터마이징했는가"가
그대로 나온다. 이게 보고서에서 가장 값나가는 재료다.

```bash
diff -rq msa-lecture/course-service/src <팀저장소>/course-service/src
```

## 출력 형식

`_workspace/01_evidence.md`에 아래 골격으로 쓴다. 해석·감상은 넣지 않는다.

```markdown
# 근거 모음

## A. 과제 범위 (교수님 코멘트)
- 인용: "..."
- 함의: 어디까지 쓰고 어디서 멈출지

## B. 아키텍처 사실
| 항목 | 값 | 출처(파일:줄) |
|---|---|---|

## C. 흐름 (이음매별)
### C-1. 로그인 → 조회 → 의뢰 → 결제 → 확정
단계별로 "무엇이 무엇을 부르는가" + 근거 파일

## D. 팀이 원본에서 바꾼 것
| 원본 | 변경 후 | 파일 |
|---|---|---|

## E. 숫자
포트 / 임계값 / 데이터 규모 / 측정치 — 전부 출처 병기

## F. 인용할 코드 조각
파일 경로 + 줄 범위 + 실제 코드 (10줄 이내로 자를 것)

## G. 트러블슈팅 후보
증상 / 원인 / 해결 — 저장소의 "알려진 한계", QA 리포트, 커밋 메시지에서 캐낸다
```

## 원칙

- **출처 없는 줄은 쓰지 않는다.** 파일:줄 또는 문서명을 반드시 붙인다.
- 확인 못 한 것은 `(미확인)`으로 남긴다. 지우면 나중에 집필자가 사실인 줄 알고 쓴다.
- 코드 인용은 10줄 이내. 그 이상은 보고서에서도 어차피 잘린다.
- 서비스 내부 로직(JPA 매핑, 암호화, 결제 처리 내부)은 파지 않는다. 실습 가이드가
  명시적으로 "몰라도 되는 것"으로 지정한 영역이다.
