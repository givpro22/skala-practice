# sLLM 서브노트 쓰기

## 서브노트가 보고서와 갈리는 지점

서브노트는 완성된 결과 보고서가 아니라 **이틀간의 실습 기록**이다. 실습 가이드 2절은
학습한 내용, 실습한 사항, 트러블슈팅 사항, 느낀점을 담으라고 적고 있다. 네 가지 중
트러블슈팅과 느낀점이 빠지면 노트가 아니라 매뉴얼 요약이 된다.

정리된 지식을 나열하지 마라. **막혔던 지점과 뚫린 순간**이 본문의 뼈대여야 한다.
`처음에는 A인 줄 알았는데 B였다` 구조가 이 문서의 엔진이다.

노트는 두 개다. 파일이 갈리는 기준은 날짜지 주제가 아니다.

| | 1일차 | 2일차 |
|---|---|---|
| 소재 | Knowledge Asset 워밍업(BGE-M3 + FAISS), LoRA 파라미터 비교 | LoRA SFT 학습, Base ↔ SFT 평가 |
| 필수 5항목 | 해당 없음 | **전부 들어간다** |
| 원고 | `_workspace/03_manuscript_day1.md` | `_workspace/03_manuscript_day2.md` |
| 분량 | A4 3~4쪽 | A4 4~6쪽 |

## 1일차 노트 골격

```
# 제목 (한 줄, 명사구)
4반 박영서                    ← 표지 줄. 자리표시자 금지

[손그림: 검색해서 답하는 흐름]  ← 본문보다 먼저. 밑에 캡션을 달지 않는다

## 학습한 내용
   sLLM 을 왜 쓰는지, RAG 와 Fine-tuning 이 각각 무엇을 해결하는지. 2~4문단

## 실습한 사항
### BGE-M3 임베딩과 FAISS 검색
   노트북에서 실제로 나온 결과. Knowledge Base 에 없는 질문에 어떻게 반응했는지
### LoRA 적용 전후 파라미터
   전체 파라미터와 학습 가능 파라미터의 실제 수치. 비율이 이 절의 요점

## 트러블슈팅
   문제 상황 / 원인 / 해결 3단 고정. 사례 2~4개. 제목은 짧은 명사

## 느낀점
   1~2문단. 마지막에 한 줄 메모
```

소주제 하나쯤은 그림만 두고 본문을 안 써도 된다.

## 2일차 노트 골격 — 다섯 항목의 순서와 이름을 바꾸지 않는다

실습 가이드 2절이 지정한 항목이다. 채점자가 이 순서로 찾는다. 제목 문구는 다듬어도
되지만 **괄호 안 키워드는 남긴다** — 게이트가 그걸로 존재를 확인한다.

```
# 제목 (한 줄, 명사구)
4반 박영서

## 1. 이해관계자 가치 (Pain Point)
   누가 무엇 때문에 불편한지 먼저. sLLM 이 왜 필요하고 SFT 가 어떤 경우에
   적용되는지, 그 가치가 누구에게 가는지. 기술 설명을 여기서 시작하지 마라

## 2. 이를 해결하기 위한 AI 솔루션
   1번의 Pain Point 를 어떤 업무 서비스로 받는지. 그 안에서 sLLM 과 SFT
   Pipeline 이 맡는 역할

## 3. 아키텍처 구성도
   [손그림]  Dataset → Base Qwen → LoRA SFT → Fine-tuned Qwen → 평가
   Train/Validation/Evaluation 셋의 흐름, Adapter 가 Base 에 결합되는 구조까지
   한 장에. 그림이 먼저 오고 설명이 뒤

## 4. Base Model vs SFT Model
   [표]      같은 질문에 대한 Keyword Score, Token F1, Total, 승패 집계
   [대조]    실제 답변 2~3쌍. 질적 차이가 눈에 보이는 것으로 고른다
   숫자만 늘어놓지 말고 무엇이 달라졌는지 한 문장으로 말한다

## 5. 평가 화면 스냅샷
   ![](01_eval_summary.png)
   무엇을 실행한 화면인지 한 줄. 화면 안 숫자를 본문에서 다시 받아 적지 않는다

## 트러블슈팅
## 느낀점
```

3번 그림과 5번 스냅샷은 성격이 다르다. 3번은 손그림이고 5번은 실제 실행 화면이다.
5번을 손그림으로 대신하면 증빙이 아니게 된다.

## 먼저 확인할 것 — 이게 있으면 원고를 다시 쓴다

사용자가 직접 반려한 항목이다. 취향 조정이 아니라 통과 조건이다. 각 항목의 대체
문장은 `references/voice-guide.md` 0절에 실제 지적 사례와 함께 있다.

| 항목 | 허용 |
|---|---|
| 본문의 큰따옴표 `"` | 0회. 코드 블록 안의 Python 문법만 예외 |
| 중간점 `·` | 0회. 나열은 쉼표로 |
| 이모지 | 0개 |
| 물음표 | 0회. 위치를 가리지 않는다. 자문자답도 안 쓴다 |
| 그림 뒤 `>` 캡션 | 0회 |
| 글이 자기를 설명하는 문장 | 0회 |
| `>` 인용 블록 | 0개 |
| 인용 앞 도입 한 줄 문단 | 0회 |
| 예고형 도입 문장 | 0회 |
| 제출자 줄 | 4반 박영서 |
| 필수 5항목 (2일차) | 5개 전부 |
| 평가 화면 스냅샷 이미지 (2일차) | 1개 이상 |

전부 기계로 셀 수 있으므로 눈으로 세지 말고 스크립트를 돌린다.

```bash
bash .claude/skills/subnote-writing/scripts/voice-gate.sh _workspace/03_manuscript_day1.md day1
bash .claude/skills/subnote-writing/scripts/voice-gate.sh _workspace/03_manuscript_day2.md day2
```

두 번째 인자를 빼면 파일명에서 유추한다. 유추가 안 되면 구조 검사를 건너뛰므로,
2일차 원고에는 반드시 `day2` 를 명시한다.

`글이 자기를 설명하는 문장` 이 자주 새어 나온다. 이런 것들이다.

- `이 노트는 학습 과정을 전부 담은 기록이 아닙니다.` — 본문이 아니라 본문 해설
- `솔직하게 적어 둡니다.` — 할 말을 하기 전에 하겠다고 예고하는 군더더기
- `그 얘기부터 하겠습니다.` / `정리하자면` — 사람은 노트에 목차 안내를 달지 않는다

발견하면 대체 문장을 찾지 말고 **줄을 통째로 지운다.**

## 사람이 쓴 글로 읽히게 하는 법

위 표를 통과했다는 전제에서, 나머지 셋이 문체를 결정한다.

**1. 문단 길이를 고르게 만들지 마라.** AI 글의 가장 큰 냄새는 모든 문단이 3~4문장으로
균일하다는 것이다. 한 문장짜리 문단을 섞어라. 특히 깨달음을 적을 때.

**2. 결론을 매 절 끝에 붙이지 마라.** `이를 통해 ~을 배울 수 있었습니다` 를 절마다
달면 사람이 아니라 템플릿이 쓴 글이 된다. 어떤 절은 그냥 사실을 적고 끝낸다.

**3. 헤매던 흔적을 남겨라.** 이 실습에는 재료가 많다. 학습이 몇 시간 걸린 것,
장치가 MPS 로 떨어진 것, 평가에서 SFT 가 오히려 진 항목이 있는 것. 매끄럽게
성공한 서술만 늘어놓으면 학습 기록이 아니라 요약본이다.

금지 어휘는 `references/voice-guide.md` 0절 끝에 있다. 반대로 화살표(→, ↔)와
느낌표, 물결표는 아끼지 않는다. 문장부호가 얌전하면 노트가 아니다.

## 숫자를 절제한다

이 실습은 숫자가 특히 많다. loss, eval_loss, 스텝, 학습률, rank, alpha, max_length,
파라미터 수, Keyword Score, Token F1, 승패, 소요 시간. 근거 파일에 다 있으니
그대로 옮기면 절마다 열 개가 넘고, 그러면 실습 노트가 아니라 논문으로 읽힌다.
사용자가 내용이 너무 심오하다고 반려한 자리가 정확히 여기다.

**본문 기준 절 하나에 측정 수치 10개 이하.** 표 안의 숫자는 세지 않는다. 넘으면
같은 축으로 비교되는 값은 표로, 구조와 분기는 그림으로 보내고, 이야기 뼈대에
안 걸리는 것은 지운다. 상세를 그림이나 표로 넘겼으면 본문이 그걸 다시 받아 적지 않는다.

## 근거 없는 문장을 쓰지 않는다

숫자, 파일 경로, 설정값, 지표는 전부 `_workspace/01_evidence.md` 에서 옮긴다.
거기 없는 사실은 쓰지 않는다.

- 평가 점수를 기억으로 적지 마라. `outputs/evaluation_summary.json` 에 있는 값이다
- Base 답변과 SFT 답변을 요약해서 옮길 때 **원문에 없는 내용을 넣지 마라**.
  잘랐으면 잘랐다고 표시한다
- 회사 고유 용어(AURORA, BLUE-7, LYNX 등)의 철자를 확인한다. 이게 Keyword Score 가
  세는 대상이라 틀리면 절 전체가 어긋난다
- 아는 만큼만 쓴다. 깊이 상한은 가이드 13절 네 줄이다. Attention 내부나 양자화
  방식을 아는 척하는 서술은 감점 요인이다

## 출력 형식

`docx-compose` 스킬이 처리하는 마크다운 부분집합만 쓴다: 제목 3단계, 문단, 불릿,
파이프 표, 코드 블록, 이미지, `---` 쪽나눔, 인라인 굵게/코드. 번호 목록과 링크는
지원되지 않는다. 번호가 필요하면 `- 1) 내용` 처럼 불릿 안에 직접 쓴다.

이미지는 `![](NN_이름.png)` 로 **파일명만** 쓴다. 다음 줄에 `> 캡션` 을 붙이지 않는다.
이름표가 필요하면 이미지 **앞** 줄에 명사구 한 줄을 둔다.

절이 바뀌는 지점에 `---` 를 넣어 쪽을 직접 끊는다. 안 넣으면 제목 하나가 앞 쪽
맨 아래에 혼자 남는다.

## 후속 요청 처리

- "이 절만 다시" → 해당 절만 고치고 나머지 문장은 건드리지 않는다. 전체를 다시 쓰면
  사용자가 이미 확인한 부분까지 바뀐다
- "분량 늘려줘" → 새 소주제를 추가하지 말고 기존 소주제에 헤맨 과정을 덧붙인다.
  소주제 개수를 늘리면 각 절이 얕아진다
- "더 사람같이" → 문단 길이 편차와 1인칭 회고 비중을 먼저 손본다. 어휘 교체는 그다음
- "1일차만 다시" → 2일차 원고를 열지 않는다. 두 파일은 독립이다
