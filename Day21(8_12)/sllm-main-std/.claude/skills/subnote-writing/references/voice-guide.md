# 목소리 가이드 — 사람이 쓴 글로 읽히기

0절은 Day19 개인과제에서 사용자가 초고를 여러 차례 보면서 하나씩 반려한 기록이다.
왼쪽 칸의 문장이 MSA 소재인 것은 그때 원고에서 나왔기 때문이고, 걸린 이유는 소재와
무관하다. 항목은 그대로 가져오고 소재만 sLLM 으로 바뀐다.

## 0. 절대 금지 — 사용자가 직접 지적한 것

이 표는 취향이 아니라 반려 사유다. 하나라도 남아 있으면 원고를 다시 쓴다.
왼쪽은 실제 원고에서 지적받은 문장이고, 오른쪽이 통과하는 형태다.

| 금지 | 실제로 지적받은 문장 | 왜 걸리는가 | 이렇게 쓴다 |
|---|---|---|---|
| **큰따옴표** | `"쟤 지금 몇 번 포트에 떠 있지?"를 누군가는 알고 있어야` | 자기 속말을 따옴표로 감싸는 건 AI가 강조를 흉내내는 방식이다 | 따옴표를 떼고 평서문으로. `어느 서비스가 몇 번 포트에 떠 있는지를 누군가는 알고 있어야 합니다` |
| **중간점 `·`** | `user·course·enrollment`, `Java·Python·Vue·SQL` | 나열을 중간점으로 묶는 건 사람이 손으로 쓰는 방식이 아니다 | 쉼표. `user, course, enrollment` |
| **물음표 전부** | `그럼 enrollment는 course가 어디 있는지 어떻게 알까요?` (문단 끝) | 처음에는 답 없이 끝나는 의문형만 반려됐는데, 사용자가 물음표 자체가 어색하다고 다시 지적했다. 위치를 가리지 않는다 | 평서문으로 바꾼다. `enrollment가 course의 주소를 어떻게 아는지가 문제였습니다.` |
| **이모지** | `... 실습의 일부라는 걸 배웠다 🙂` | 어색하다는 지적을 받았다 | 이모지만 뗀다. 문장은 그대로 둬도 된다 |
| **글에 대한 해설** | `이 보고서는 그 열 개를 하나씩 다 이해한 기록이 아닙니다.` | 본문이 아니라 본문 사용설명서다. 독자에게 읽는 법을 지시하고 있다 | 그 줄을 지우고 바로 본론. `실습 가이드에도 이해가 안 되는 것이 정상이라고 적혀 있습니다.` |
| **말 꺼내기 전 예고** | `솔직하게 적어 둡니다.` | 할 말을 하기 전에 하겠다고 알리는 군더더기 | 지우고 바로 내용. `LoRA가 왜 rank 16이어야 하는지는 아직 설명 못 합니다.` |
| **그림 밑 해설 캡션** | `> enrollment는 course의 주소를 모른다. lb://course-service 라는 이름만 안다.` | 그림에 자막을 다는 건 발표자료 문법이다 | 캡션을 지운다. 그림이 뭔지 밝혀야 하면 그림 **앞** 줄에 명사형 이름표만 (`LoRA Adapter 결합 구조`) |
| **인용 앞 뜸들이기** | `실습 가이드는 이 당황을 미리 예상하고 있었습니다.` — 뒤에 `>` 인용 블록이 붙는다 | 한 줄 도입 + 인용 + 한 줄 도입 + 인용이 반복되면 혼잣말이 된다. 사용자가 독백이 많다고 반려한 자리가 정확히 여기다 | 출처를 앞 문단 **문장 안**에 넣고 인용 블록은 세우지 않는다 |
| **`>` 인용 블록 전부** | `> 이걸 깊게 파지는 않겠지만 필요한 이유는 알겠어. 충분해요.` (교수님 발언, 축자) | 상한을 4→2→0 으로 세 번 내렸다. 축자이고 구어체 어투 자체가 정보였는데도 반려됐다 — 남의 말을 떠 오면 그 대목만 어투가 붕 뜨고, 이 문서는 그 말을 한 사람이 읽는다 | 블록을 통째로 지우고 사실만 앞 문단에 녹인다. 녹일 게 없으면 그냥 지운다 |
| **사람 발언을 출처로 대기** | `교수님도 같은 선을 그으셨습니다.` | 인용 부호를 떼도 반려됐다. 대화에서 나온 말은 출처를 밝히는 순간 같은 문제가 생긴다 | 문서에 적힌 근거(실습 가이드, 코드 주석, readme)로 대신하거나, 그 문장을 지운다 |
| **의역을 인용 블록에 넣기** | 코드 주석을 요약해서 다시 쓴 문장을 `>` 안에 넣은 것 | 옮긴 게 아니라 다시 쓴 문장이라 어투가 본문(경어체 노트)과 달라서 이 대목만 AI가 쓴 것처럼 읽힌다 | 인용 부호를 떼고 본인 문장으로 푼다 |

추가로 걸리는 어휘 — 나오면 즉시 다시 쓴다.

뿐만 아니라, 나아가, 이를 통해 ~할 수 있었습니다(반복), 중요한 것은 ~라는 점입니다,
단순히 ~이 아니라 ~입니다(반복), 결론적으로, 종합하면, ~에 대한 깊은 이해를 얻었습니다,
핵심은 ~이다(반복), 앞으로도 ~하겠습니다

### 인용은 어떻게 하나

**`>` 인용 블록은 원고 전체에서 0개다.** 상한이 4에서 2로, 2에서 0으로 내려왔다.
세 번 다 같은 사용자가 같은 이유로 반려했으니 이제 조건부가 아니다.

마지막까지 남아 있던 한 개는 교수님 발언을 축자로 옮긴 것이었고, 앞선 검수에서
남을 자격이 있다고 판정받은 것이었다. 축자였고 구어체 반말 자체가 선을 그은
행위였다. 판정 기준으로는 통과였는데 사용자는 반려했다. **기준이 틀렸던 것이다.**

남의 말을 그대로 떠 오면 어투가 본문과 달라 그 대목만 붕 뜬다. 축자일수록 더 뜬다.
그리고 이건 제출물이고, 그 말을 한 당사자가 읽는다.

인용할 사실은 전부 서술로 푼다. 출처는 앞 문장 안에 넣는다.

```
반려 —
  실습 가이드에 이렇게 적혀 있습니다.

  > Base LLM 은 우리 회사의 고유 규정을 원래 알지 못합니다.

통과 —
  실습 가이드에는 Base LLM 이 회사 고유 규정을 원래 알지 못한다고 적혀 있습니다.
  읽을 때는 당연한 말인 줄 알았는데, Base 답변을 직접 보니 모른다기보다
  아는 것처럼 지어내는 쪽이었습니다.
```

**사람의 발언은 서술로도 넣지 마라.** 문서에 적힌 것(실습 가이드, readme, 코드 주석,
노트북 마크다운 셀)은 서술로 인용해도 되지만, 대화에서 나온 말은 출처를 밝히는
순간 같은 문제가 생긴다.

문장 한복판에 짧게 끼워야 하면 홑따옴표를 한 번까지 쓴다.

### 한 줄 문단과 독백은 다르다

한 문장짜리 문단은 이 문서가 권장하는 리듬이다(4개 이상). 그런데 같은 한 줄이라도
**다음에 올 말을 예고만 하는 줄**은 독백이라 반려된다. 구분은 그 줄을 지웠을 때
사실이 사라지느냐다.

- 남긴다 — `학습 가능한 파라미터가 1퍼센트 아래로 떨어지는 걸 눈으로 보고서야 LoRA가
  왜 어댑터라고 불리는지 알았습니다.` (판단이 들어 있다)
- 지운다 — `여기서 제가 놓치고 있던 게 있었습니다.` / `한 가지 더 배운 게 있습니다.`
  (지워도 뒤 문장이 그대로 산다)

지운 자리는 대체 문장으로 메우지 말고 바로 본론을 잇는다.

### 물음표는 쓰지 않는다

위치를 가리지 않는다 — 문장 끝, 문장 한복판, 제목, 자문자답 전부다. 질문을 던지는
리듬이 필요하면 명사구로 바꾸고 답을 화살표 뒤에 붙이면 형태가 유지된다.

```
반려 —  SFT를 왜 하는가? → 회사 고유 규정을 모델에 넣기 위해
통과 —  SFT를 하는 이유 → 회사 고유 규정을 모델에 넣기 위해
```

화살표는 그대로 살린다. 물음표만 뗀다.

제목도 마찬가지다. `LoRA는 왜 가벼운가` 대신 `LoRA가 가벼운 이유` 처럼 명사구로
바꾼다. 어미가 의문형이면 물음표를 안 달아도 걸린다.

## 1. 통과한 노트가 실제로 쓴 문장들

Day19 개인과제의 원본 템플릿2에서 뽑은 것이다. 소재는 다르지만 온도는 그대로 가져온다.

- `처음에는 로컬 설정이 편하다고 느꼈지만, 팀 협업이나 운영 환경으로의 확장을
  고려할수록 Docker의 장점이 확실히 느껴졌습니다.`
- `RestAPI가 바~로 그 표준화된 규칙(약속)!!!`
- `즉, 프론트는 API를 읽고, 이해하고, 요청을 보내고, 응답을 받아 처리할 수 있어야 한다!`
- `처음에는 pydantic 모델로 스키마를 정의하는 것이 단순히 필드 나열이라고 생각했지만,
  스키마 자체가 개발자 간의 공통 언어라는 것을 깨달았습니다.`
- `그래서 결론은~!!!`
- `+ 파일 저장 누르는 것 잊지 말기`

여기서 읽어낼 것:

1. **경어체 본문 + 반말 메모가 섞인다.** ~습니다로 쓰다가 요점 정리에서
   ~이다!, ~하기! 로 툭 떨어진다. 이 낙차가 필기 노트의 질감이다.
2. **화살표(→, ↔)와 느낌표를 실제로 쓴다.** 문장부호가 얌전하면 노트가 아니다.
   `바~로`, `사실~!` 처럼 물결표도 쓴다.
3. **처음에는 A라고 생각했는데 B였다** 구조가 반복된다. 이게 이 문서의 엔진이다.

안 쓰는 문장부호: 물음표, 중간점, 큰따옴표. 원본에 있다는 사실은 근거가 되지 못한다.
세 번 다 사용자가 직접 반려했다.

## 2. 문단 리듬

한 절 안에서 문단 길이를 다르게 섞는다. 예시 배열:

```
4문장 문단  (상황 설명)
1문장 문단  (깨달은 것)
3문장 문단  (그래서 어떻게 했는지)
불릿 3~4개  (정리)
1문장       (한 줄 메모)
```

**모든 절을 이 배열로 쓰면 그것도 균일해진다.** 어떤 절은 불릿 없이 서술만,
어떤 절은 불릿만 있고 서술이 두 줄인 식으로 절마다 형태를 달리해야 한다.

## 3. 문장 단위 체크

| 냄새 | 고치는 법 |
|---|---|
| "~을 통해 ~을 할 수 있습니다" 3회 이상 | 절반을 "~하면 ~가 됩니다" 같은 직접 서술로 |
| 모든 절이 요약 문장으로 끝남 | 절반은 사실 서술로 끝내고 요약을 생략 |
| 병렬 구조가 완벽함 (A하고, B하고, C한다) | 하나를 문장 밖으로 빼서 따로 쓴다 |
| 형용사가 다 긍정적 (효율적인, 강력한) | 실제로 불편했던 점을 한두 개 넣는다 |
| 주어가 전부 "이 기술은" | 절반을 나는/우리는 으로 |
| 문단이 자기 글을 설명함 | 그 문단을 통째로 지운다. 대체 문장을 찾지 말고 지운다 |

마지막 줄이 제일 자주 위반된다. 글이 자기 자신을 소개하거나(이 노트는), 앞으로
할 말을 예고하거나(그 얘기부터 하겠습니다), 방금 한 말을 정리하면(정리하자면)
전부 여기 걸린다. 사람은 노트를 쓸 때 그런 안내를 달지 않는다.

## 4. 완결된 이해인 척하지 않기

이해의 깊이 상한은 실습 가이드 13절 `실습에서 이해해야 할 핵심` 네 줄이 정한다.
Base LLM 이 회사 규정을 모른다는 것, SFT Dataset 이 질문-응답 행동을 학습시킨다는 것,
LoRA 가 적은 파라미터만 학습한다는 것, 같은 Evaluation Dataset 으로 전후를 비교한다는 것.
여기까지가 이번 실습의 범위다.

Attention 내부 수식이나 QLoRA 양자화 방식을 아는 척하는 서술은 감점 요인이다.

- 통과 — `q_proj, k_proj, v_proj, o_proj 에 어댑터가 붙는다는 건 설정에서 봤는데,
  왜 하필 이 네 곳인지는 아직 모릅니다. 다만 전체를 다시 학습하지 않고도 답변 성격이
  바뀐다는 건 평가 점수로 확인했습니다.`
- 반려 — `LoRA는 사전학습 가중치를 동결하고 저차원 분해 행렬을 주입하여 downstream
  적응 시 파라미터 효율성을 확보하는 기법으로, rank r이 내재 차원을 근사합니다.`

두 번째 문장은 위키를 옮긴 것이고, 첫 번째만 학습 기록이다.

모르는 걸 적을 때 예고를 붙이지 않는다. `솔직하게 적어 둡니다` 없이 바로
`왜 이 네 곳인지는 아직 모릅니다` 로 시작한다.

### 근거를 다 넣으면 심오해진다

사용자 반려: **내용이 너무 심오하다. 조금 더 가볍게.**

근거 파일이 두꺼우면 절 하나에 측정 수치를 스무 개씩 이어 붙이게 된다. 문장마다
틀린 말은 없는데, 읽는 사람이 숫자를 계속 붙잡고 따라가야 해서 실습 노트가 아니라
논문으로 읽힌다. 반려된 절은 본문에만 수치가 26개 있었다.

이 실습은 숫자가 특히 많다. loss, eval_loss, 스텝, 학습률, rank, alpha, max_length,
파라미터 수, Keyword Score, Token F1, Total, 승패 집계, 소요 시간. 전부 근거 파일에
있으니 그대로 옮기면 절마다 열 개가 넘는다.

**절 하나에 열 개를 넘기지 마라.** 표 안의 숫자는 세지 않는다 — 표는 눈이 훑고
지나가지만 문장 속 숫자는 하나씩 읽히기 때문이다. 넘으면 셋 중 하나로 뺀다.

| 어디로 | 무엇을 |
|---|---|
| 표 | 같은 축으로 비교되는 값들. Base ↔ SFT 지표 대비가 정확히 이것이다 |
| 그림 | 구조와 분기. LoRA 결합 구조, 파이프라인 흐름, 파라미터 비율 |
| 삭제 | 이야기 뼈대에 안 걸리는 곁가지 |

기준은 **이 절의 이야기 뼈대에 이 숫자가 걸려 있는가** 다. Base vs SFT 절의 뼈대가
`Base는 일반론을 폈다 → SFT는 코드명을 답에 넣었다 → Keyword Score가 그 차이를 잡았다`
라면 걸린 숫자는 양쪽 Keyword Score 둘뿐이다. 나머지는 표로 간다.

숫자를 뺀 자리에 설명을 채우지 마라. 그냥 짧아지면 된다. 그리고 상세를 그림에 넘겼으면
본문이 그 내용을 다시 받아 적지 않는다.

## 5. 마지막 점검

위쪽 항목은 눈으로 세지 말고 스크립트를 돌린다. 하나라도 0이 아니면 통과가 아니다.

```bash
bash .claude/skills/subnote-writing/scripts/voice-gate.sh _workspace/03_manuscript_day2.md day2
```

| 본문의 큰따옴표 `"` | 0개 (코드 블록 안의 Python 문법은 예외) |
| 중간점 `·` | 0개 |
| 이모지 | 0개 |
| 물음표 (위치 무관) | 0개 |
| 그림 뒤 `>` 캡션 | 0개 |
| `>` 인용 블록 | 0개 |
| 인용 앞 도입 한 줄 문단 | 0개 |

| 평가 화면 스냅샷 이미지 (2일차) | 있음 |
