# 깊이 상한 — 어디까지 이해하고 어디서 멈출 것인가

근거: `~/Desktop/닥스/Agile_MSA_실습_가이드_수정 (1).pdf` 2~3절, `1.Agile_MSA_진행_가이드.pdf`

## 이 과제가 요구하는 것

실습 가이드에 이렇게 적혀 있다.

> 제공된 백엔드 코드를 한 줄씩 읽으며 이해하려는 시도는 이번 실습 범위를 벗어난 것이며,
> 이해가 안 되는 것이 정상입니다.

목표는 MSA 인프라를 설계·구현하는 능력이 아니라, **이미 만들어진 MSA 구조를 가져다 쓰는 능력**이다.
그래서 보고서도 "내부를 얼마나 파헤쳤는가"가 아니라 "무엇을 호출하면 무엇이 바뀌는지 아는가"를 보여야 한다.

깊이를 낮추라는 말은 **일반론으로 도망가라는 뜻이 아니다.**
포트·엔드포인트·상태 변화는 정확히 쓰되, 그 아래 구현으로 내려가지 않는다는 뜻이다.

## 서비스별 경계선

가이드 3절의 표를 그대로 옮긴 것이다.

| 구성요소 | 보고서에 써도 되는 것 | 쓰지 않는 것 |
|---------|------------------|-----------|
| user-service | 회원가입·로그인 요청 형식, 응답으로 오는 토큰 | 비밀번호 암호화 로직, DB 내부 구조 |
| course-service | 과목 등록·조회 API 형식 | JPA 매핑, 내부 쿼리 |
| enrollment-service | "신청하면 이벤트가 발생하고, 결제 후 자동으로 상태가 바뀐다"는 흐름 | Kafka Producer/Consumer 코드 |
| payment-service | 결제 완료 호출 → 이후 enrollment 상태가 바뀐다는 결과 | 결제 처리 내부 로직 |
| auth-server / api-gateway / eureka-server | 로그인하면 토큰이 나오고, 헤더에 넣으면 다른 API가 동작한다는 사용법 | 내부 설정, 서명 알고리즘, 서비스 등록 방식 |

auth-server와 api-gateway는 이미지로만 배포되고 소스가 없다.
소스가 없는 것을 설명하려 들면 반드시 추측이 섞인다. 사용법 선에서 멈춘다.

## 판단이 애매할 때

한 문장을 쓸지 말지 헷갈리면 이렇게 묻는다.

**"이 문장을 지우면, 이 시스템을 쓰는 데 지장이 생기는가?"**

- 지장이 생긴다 → 쓴다 (예: "결제가 끝나야 수강 상태가 ACTIVE로 바뀝니다")
- 지장이 없다 → 뺀다 (예: "EnrollmentKafkaConsumer가 @KafkaListener로 토픽을 구독합니다")

## 예외: 3장 트러블슈팅

3장만은 깊이 상한을 적용하지 않는다.
본인이 실제로 그 안까지 들어가서 해결했다면, 들어간 만큼 쓴다.
겪은 것을 얕게 쓰는 것도 정직하지 않다.

## 흔한 위반 두 가지

**너무 깊다:** 클래스 이름과 메서드 시그니처를 나열하고, 어노테이션 동작을 설명한다.
→ 가이드가 "몰라도 되는 것"으로 분류한 영역이다. 분량은 늘지만 평가 기준과 어긋난다.

**너무 얕다:** "MSA는 서비스를 독립적으로 배포할 수 있는 구조입니다" 수준에서 끝난다.
→ 이 프로젝트를 안 봐도 쓸 수 있는 문장이다. 포트 번호 하나, 실제 호출 순서 한 줄이 이런 문단 열 개보다 낫다.
