# msa-report — 코드이해 개인과제 보고서 오케스트레이터

조사 → 집필 → 검수 → docx 출력까지 한 흐름으로 진행한다.

**실행 모드:** 서브 에이전트 (Phase 2는 병렬, 나머지는 순차)
세 역할이 실시간으로 주고받을 것이 없고 파일로 넘기면 충분하므로, 팀 통신 오버헤드를 두지 않는다.

## 기본 경로

| 항목 | 경로 |
|------|------|
| 참고 자료 | `~/Desktop/닥스/` |
| 템플릿 원본 | `~/Desktop/닥스/코드이해_개인과제_템플릿3.docx` |
| 대상 프로젝트 | `Day19(8_10)/msa-lecture` |
| 중간 산출물 | `_workspace/` |
| 최종 출력 | `~/Desktop/닥스/코드이해_개인과제_<이름>.docx` |

사용자가 다른 경로를 주면 그것을 쓴다.

## Phase 0. 컨텍스트 확인

`_workspace/`를 먼저 확인해서 무엇을 할지 정한다.

| 상황 | 실행 |
|------|------|
| `_workspace/` 없음 | 초기 실행 — Phase 1부터 전부 |
| 있음 + "3장만", "문체만" 같은 부분 요청 | 부분 재실행 — 해당 Phase만 |
| 있음 + 새 입력(다른 프로젝트, 새 팩트) | `_workspace/`를 `_workspace_prev/`로 옮기고 초기 실행 |
| 있음 + 그냥 "다시" | 무엇을 바꿀지 사용자에게 먼저 묻는다 |

중간 산출물은 지우지 않는다. 무엇이 언제 바뀌었는지 추적할 수 있어야 검수가 가능하다.

## Phase 1. 사용자 정보 확인

보고서에 반드시 들어가야 하는데 코드에서 알 수 없는 것을 먼저 묻는다.

1. 반 / 이름 (표지 줄에 들어감)
2. 실습하며 실제로 막혔던 일 — 3장의 재료
3. (선택) 팀 아이디어 도메인 — 1장을 팀 주제로 치환할지 여부

2번은 물어도 "기억 안 난다"는 답이 흔하다. 그럴 때는 Phase 2에서 로그와 히스토리를 뒤져
후보를 찾아온 다음, "이런 게 있었는데 맞나요?"로 다시 확인한다. 처음부터 창작하지 않는다.

## Phase 2. 근거 수집 (병렬)

`report-researcher` 에이전트를 `model: "opus"`로 호출한다. 두 갈래를 병렬로 돌린다.

- **A. 프로젝트 조사** — 서비스 구성, 포트, 엔드포인트, 요청 흐름, 기동 방법
- **B. 트러블슈팅 흔적 수집** — docker 로그, 쉘 히스토리, git 로그, 수정된 설정 파일

두 결과를 `_workspace/01_researcher_facts.md` 하나로 합친다.

조사 전 `references/depth-ceiling.md`를 읽게 한다. 이 파일 없이 조사시키면
Kafka 컨슈머 코드까지 파고들어 쓰지도 못할 내용을 잔뜩 가져온다.

**게이트:** 팩트시트에 `[필요]` 항목이 있으면 Phase 3으로 넘어가기 전에 사용자에게 묻는다.
답을 못 받으면 해당 부분은 `**[확인 필요]**` 표시를 남긴 채 진행한다. 임의로 채우지 않는다.

## Phase 3. 집필

`report-writer` 에이전트를 `model: "opus"`로 호출한다. 입력은 팩트시트와 Phase 1의 답.

산출물: `_workspace/02_writer_draft.md` (템플릿3 소스 포맷)

## Phase 4. 검수

`report-reviewer` 에이전트를 `model: "opus"`로 호출한다.
양식 → 사실 근거 → 깊이 → 문체 순으로 본다.

산출물: `_workspace/03_reviewer_notes.md`

**치명** 항목이 있으면 Phase 3으로 돌아간다. 최대 2회까지만 왕복한다.
2회에도 남으면 남은 항목을 사용자에게 보고하고 진행한다. 무한 루프보다 미완성 보고가 낫다.

## Phase 5. docx 출력

`report-template3` 스킬의 변환 스크립트를 쓴다.

```bash
python3 .claude/skills/report-template3/scripts/build_docx.py \
    _workspace/02_writer_draft.md \
    ~/Desktop/닥스/코드이해_개인과제_<이름>.docx
```

변환 후 텍스트를 다시 뽑아 장·절 제목이 다 들어갔는지 확인한다(방법은 `report-template3` 스킬 참조).
원본 템플릿 파일은 덮어쓰지 않는다.

## Phase 6. 보고

사용자에게 전달할 것:

- 출력 파일 경로
- `**[확인 필요]**`가 남은 위치 목록 — 사용자가 직접 채워야 하는 곳
- 검수에서 넘어간 항목이 있으면 그 내용

마지막에 고칠 곳이 있는지 한 번 묻는다. 강요하지는 않는다.

## 데이터 흐름

```
Phase 1 (사용자 답)
      ↓
Phase 2 → _workspace/01_researcher_facts.md
      ↓
Phase 3 → _workspace/02_writer_draft.md
      ↓
Phase 4 → _workspace/03_reviewer_notes.md ──(치명 있음)──┐
      ↓                                                  │
Phase 5 → ~/Desktop/닥스/코드이해_개인과제_<이름>.docx      └→ Phase 3 (최대 2회)
```

## 에러 핸들링

| 상황 | 대응 |
|------|------|
| 템플릿 docx를 못 찾음 | 멈추고 경로를 묻는다. 비슷한 파일로 대체하지 않는다 |
| 프로젝트 경로를 못 찾음 | 멈추고 경로를 묻는다 |
| 에이전트 실패 | 1회 재시도. 재실패 시 그 부분을 비운 채 진행하고 보고서에 누락을 명시한다 |
| 트러블슈팅 재료가 전혀 없음 | 3장을 창작하지 않는다. 사용자에게 질문 목록을 넘기고 나머지 장을 먼저 완성한다 |
| 팩트시트와 초안이 충돌 | 팩트시트를 기준으로 초안을 고친다. 반대 방향은 안 된다 |
| docx 변환 실패 | 마크다운 초안을 그대로 전달하고 실패 원인을 보고한다 |

## 테스트 시나리오

**정상 흐름**
입력: "닥스 폴더 참고해서 코드이해 개인과제 템플릿3 양식으로 보고서 써줘"
기대: Phase 0에서 초기 실행 판정 → 반/이름 질문 → 팩트시트 생성 → 초안 → 검수 →
docx 생성 → 확인 필요 항목 목록과 함께 보고

**에러 흐름**
입력: 같은 요청, 단 컨테이너가 한 번도 뜬 적 없어 로그가 없음
기대: Phase 2-B가 흔적을 못 찾고 `[필요]`로 분류 → Phase 2 게이트에서 사용자에게 질문 →
답이 없으면 3장을 `**[확인 필요]**`로 비운 채 1·2장을 완성하고, Phase 6에서 비운 위치를 명시.
그럴듯한 오류 사례를 지어내면 실패로 본다.

**부분 재실행**
입력: "3장에 어제 겪은 포트 충돌 얘기 추가해줘"
기대: Phase 0에서 부분 재실행 판정 → 팩트시트 E절만 갱신 → 3장만 다시 씀 →
1·2장 문장은 그대로 유지 → docx 재생성
